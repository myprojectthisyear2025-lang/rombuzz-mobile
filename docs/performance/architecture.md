# Instrumentation architecture

## Backend

`server/performance/context.js` uses AsyncLocalStorage and `performance.now()` to associate bounded spans with one server-generated request UUID. Instrumentation is off unless `PERF_DIAGNOSTICS=true`. `PERF_SAMPLE_RATE` is clamped to 0..1; default 1 when enabled. A request holds at most 256 spans. Overflow is counted. No incoming correlation value is trusted or echoed.

`http.js` runs before CORS and Express body parsers. It observes existing `res.json`, `res.send` and `res.writeHead`, preserving their arguments, results, status and response bodies. JSON serialization is timed around Express's existing implementation, without serializing again. The header boundary closes outstanding spans; subsequent fire-and-forget work is excluded from the response critical path. Finish/abort is separately recorded. Header time is not proof of bytes reaching the device.

`express.js` wraps registered leaf handlers after all routes and error middleware have been installed. Current Express 5 router traversal preserves function arity, `next`, promise rejections and error propagation; regression tests exercise these contracts. Each middleware is named from its existing function, and `authMiddleware` has its own category. Route functions remain inclusive parent spans. Unknown CPU/filter work remains honestly labeled `handler`; it is not invented as query or CPU time. Discover's existing filter/score and sort/transform/sign blocks have two explicit reusable spans.

The response gains `X-Perf-Request-Id` and `Server-Timing` only for sampled diagnostic requests. CORS exposes those headers only in diagnostic mode. Header categories are `auth`, `middleware`, `mongo`, `hydrate`, `logic`, `serialize`, and `total`; interval unions prevent overlap within each category from being counted twice. Categories themselves overlap. Never add auth + Mongo + hydration to get total.

One `[PERF]` JSON record is logged per sampled response, with route template, request ID, status, header/finish time, query/command counts, payload byte count where Content-Length exists, intervals and overflow count. No bodies, tokens, authorization headers, database URI, query predicates, messages, account IDs, location values or signed URLs are recorded. Dynamic route segments use templates. Existing application logging is unchanged and outside this diagnostic format.

`runtime.js` supplies process CPU deltas, event-loop utilization and a rolling one-second event-loop-delay p99 (20 ms sampling resolution). These describe the process, including concurrent work; they are not exclusive request CPU attribution. Timers are unref'd and exist only in diagnostic mode.

## MongoDB methodology

`mongo.js` wraps existing Mongoose `Query.exec`, `Aggregate.exec`, `save`, and the `$save` create alias. Labels contain model and operation names only. Logical spans include connection/pool waiting, driver/network, BSON/materialization, Mongoose hydration/hooks and application scheduling. They cover finds, counts, aggregates and writes actually invoked through those methods. Driver monitoring separately observes find/getMore/aggregate/count/distinct/insert/update/delete/findAndModify commands without reading command documents or replies. Low-level commands outside the allowlist or outside a request are not covered.

Outer document `$init` calls are measured synchronously, excluding recursive double counting. This identified full embedded-room hydration as a material cost in the local fixture. It is not a measure of every allocation or all BSON decoding. Driver spans are nested inside logical operations; concurrent commands overlap. Logical query count differs from wire-command count, especially for cursors and aggregate-backed count operations. Populate can manifest as multiple operations; no populate/lookup bottleneck was established here.

The local runner executes six selected `explain('executionStats')` queries after timing, only against its disposable synthetic database, with `maxTimeMS(1000)`. Plans report index/stage, returned/examined documents, keys and database execution time. No production explain ran, and the application never automatically issues explain. Do not generalize tiny-fixture selectivity to Atlas. Future slow-query analysis should use one reviewed query shape on staging, bounded time and representative cardinality, then confirm actual deployed indexes. No index recommendation is supported by this small baseline alone.

## Mobile

Six modules under `src/performance/diagnostics` provide core events, network, screen/render, cache, media and socket observation. Enable with `EXPO_PUBLIC_PERF_DIAGNOSTICS=true`. Release builds additionally require `EXPO_PUBLIC_PERF_ALLOW_RELEASE=true`. Flags are build-time Expo values: restart Metro/rebuild when changing them. Default builds emit no diagnostic events. Disabled media/screen factories return the original component and disabled reader factories return the original reader.

`core.ts` keeps up to 3,000 events in memory; further events increment `dropped`. Nothing uploads. Export manually with `globalThis.__RBZ_PERF__.snapshot()` or `.flush()`. `.clear()` clears records; it does not clear application caches or restart the JS clock. Use a short capture per flow and check dropped counts. Milestones use monotonic JS time; cache age uses existing wall-clock savedAt metadata.

Tap markers cover main bottom navigation, Home actions, LetsBuzz sub-tabs, inbox open and Social Stats profile actions. Screen wrappers record focus/mount/unmount and React Profiler commit measurements. Readiness hooks observe the existing screen state predicates and record cache/fresh state scheduling, commits and a double-requestAnimationFrame opportunity. These are **JS/React milestones, not native pixels**. An empty or error-state predicate may be ready; inspect the recording before calling it useful content. Some navigation entry points have no explicit tap marker; their focus starts the visit. Screen eager mounting and focus are intentionally distinct.

React Profiler `actualDuration` is render work, not total native layout/paint or state scheduling delay. Production React builds may not provide Profiler callbacks; absence means unavailable, not zero. Development/StrictMode overhead must be distinguished from a profiling-capable release measurement. No rerender count or expensive list claim is made without a real capture.

`network.ts` wraps the existing fetch once, only for the configured API origins, and calls it with the original arguments. It preserves existing Sentry interception, authentication, headers, retries and cache behavior. It records request start, response resolution, status, allowed Server-Timing fields, UUID, and body consumption. It never pre-consumes the body. Existing `text` and `json` calls are observed when the application invokes them. The shared rbzApiClient separately times its explicit JSON.parse. For direct `response.json`, body consumption and parsing are combined; streams/blob/clone consumers are not timed.

React Native fetch resolution may already include buffered body work depending on its implementation. `http-headers` therefore means the JS fetch-resolution boundary, not guaranteed first-byte arrival. Exact DNS/TCP/TLS timings are unavailable through this API. Client duration minus `Server-Timing.total` is approximate non-server elapsed time, including scheduling, connection/transport and body transfer, not pure RTT or a proof of Render delay. Existing Axios-based login/signup/upload paths are outside this fetch observer; their backend requests and existing Sentry HTTP instrumentation remain available, but this audit does not claim fine-grained client auth/upload timings.

The response UUID joins a mobile HTTP event to its backend trace without changing outbound headers. A request's foreground screen is an **association**, not proof of its initiating component: startup/background requests can overlap navigation. A bounded exact-URL map flags repeated GETs within two seconds and whether their fetch-resolution intervals overlap. URL/query values never leave memory. A duplicate flag is evidence to inspect, not automatic proof a refresh is unnecessary.

Cache helpers time existing memory/persisted reads, hit/miss and age where provided, preserving all values and TTL logic. They cover shared rbzCache, Discover deck, LetsBuzz feed, chat-thread caches and Home greeting; startup auth storage has its existing combined span. Fresh request/body and fresh-state markers bracket refreshes. There is no new caching policy and no comprehensive instrumentation of every unrelated SecureStore key/write.

## Media and sockets

Image/video factories preserve native component props, refs and callbacks. Representative avatars, Discover/profile/gallery images, post media, reel thumbnails/video, chat/shared/purchased media and gift cards use them. Image load-start/load/end/error events include reported dimensions; video records load and ready-for-display with natural dimensions. These combine several native stages and do not individually isolate download, decode, layout or actual viewability. An offscreen image can load. Pair with a native recording/frame trace before declaring it visible.

Only role/provider, opaque media/resource IDs, elapsed time and dimensions are exported. A bounded internal URL map lets captures associate repeated mounts; it is not proof of repeated network transfers. Custom R2 domains classify as other-remote unless recognizable. Existing prefetch calls and native cache headers are unchanged; native transfer/cache proof requires a network capture or the explicit media probe.

Socket observation adds one passive observer per socket through a WeakSet: connect/reconnect/error/disconnect durations, live connection count and existing listener counts at connection. It never records packet contents or changes options, emit logic, business listeners or cleanup. It does not instrument server-side socket handler CPU/Mongo spans, typing delivery, or native bubble display. The local runner separately measures authenticated handshake and HTTP-send-to-peer-event time. Existing socket regression tests validate realtime behavior.

## Sentry and production safety

The latest backend already initializes `@sentry/node` before Express/Mongoose in `instrument.js`; installed SDK source includes HTTP, Express, Mongo and Mongoose tracing integrations when tracing is enabled. Existing `SENTRY_TRACES_SAMPLE_RATE` defaults to 0.1. Mobile Sentry already captures HTTP traces, uses 1.0 in development/0.1 otherwise, and propagates traces to the configured Render origin. Existing initialization, sampling, error handler and privacy functions are untouched.

This audit adds only a diagnostic UUID attribute to an existing active Sentry span and records its trace ID when present. It creates no parallel Sentry transactions or duplicate custom database spans. Use existing Sentry traces to locate slow routes and correlate the UUID with local detail. The synthetic runner deliberately leaves SENTRY_DSN blank, so no Sentry ingestion or production trace was verified. The existing beforeSend error sanitizer alone does not establish transaction/span privacy; review that existing telemetry path separately before expanding production trace collection.

Detailed diagnostics remain off in production by default. If later enabled for a bounded staging capture, sample deliberately and export short sessions. Do not enable 100% verbose tracing indefinitely. Flags off remove detailed wrapping/command monitoring after process restart; no persistence/schema cleanup is necessary. Local overhead observations and disabled-mode tests are in [baseline.md](baseline.md) and [validation.md](validation.md).
